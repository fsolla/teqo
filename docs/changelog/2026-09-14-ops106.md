**OPS106 — Falha do `verify` dispara agente autônomo de desbloqueio (single-flight) (2026-09-14):** um `verify` vermelho do deploy deixou de ser um beco sem saída — o workflow novo `.github/workflows/auto-unblock.yml` (`workflow_run` no Deploy; só `push` em `main`, e só quando o job `verify` é quem falhou, conferido pela jobs API) dispara UM agente no homeserver com o mesmo contexto de `pnpm worktree fix`. O job instala as deps do checkout (`pnpm install --frozen-lockfile`) antes do launcher — o wrapper carrega `scripts/worktree.mjs` (`dotenv`/`pg` no load) e o checkout self-hosted é limpo a cada run. Launcher `scripts/auto-unblock.sh` (flock próprio `/tmp/teqo-unblock.lock`, nunca o lock do deploy) + `scripts/auto-unblock.mjs` (cria/comenta/fecha a Issue token `auto-unblock` que linka o run vermelho — o token aberto + o lock são o single-flight; falha com agente ativo só comenta, nunca enfileira; TTL de 3h reclaima órfão) e wrapper destacado `scripts/auto-unblock-agent.mjs` (fd 9 herdado mantém o lock, `RUNNER_TRACKING_ID` removido, stdio no log `~/teqo-unblock/logs/unblock-<run-id>.log`, cap de 4h com SIGTERM→SIGKILL) — o job termina em ~1 min e não prende o slot do runner. O agente provisiona o worktree pelo dono (`scripts/worktree.mjs fix --headless --directive`, mesma rota do humano), aplica guard fail-closed de banco (host local + nome `teqo_wt*`/`*_test`; `DATABASE_URL`/`ALLOW_REMOTE_DB`/`TEQO_ENV` removidos do env) e roda `opencode run --command bug-fix` com o report do run; push/PR usam o `AUTOMERGE_PAT` só no processo destacado, via credential helper por env (nada persistido no `.git`). Sem PR ao fim, o token vira `blocked` (gate humano); `deploy.yml`, `verify` e `deploy-homeserver.sh` ficam intocados — nenhum auto-retry do deploy e produção segue só com approval humano.
