**OPS104 — Disparo automático do deploy pós-merge (staging automático, produção com review) (2026-09-14):** publicar deixou de depender de alguém lembrar do dispatch — o `deploy.yml` agora nasce no merge e converge sozinho, sem nunca auto-aprovar produção. **Trigger 1:** `push` em `main` somado ao `workflow_dispatch` (escape manual preservado); o job hosted `preflight` (`scripts/deploy-preflight.mjs`) pula o run quando já existe outro deploy `queued`/`in_progress` — um run `waiting` de approval **não** conta (merge nessa janela começa um run novo e os dois ficam pendentes para o humano escolher), e falha de API é fail-open (o guard é dedupe, não gate). **Trigger 2:** depois do `deploy-staging` verde, o job hosted `requeue` (`scripts/deploy-requeue.mjs`, **fora** do grupo `deploy-homeserver` — um approval pendente não pode bloquear a convergência) lê o head de `main` e re-despacha o workflow se um merge chegou durante o verify/staging; falha é fail-red. A lógica de decisão é pura (`scripts/lib/deploy-trigger.mjs`; `ACTIVE_RUN_STATUSES`, `decidePreflight`, `decideRequeue`) e o client `scripts/lib/github-api.mjs` ganhou `listWorkflowRuns`/`getBranchHead`; dispatch usa o `GITHUB_TOKEN` nativo (`workflow_dispatch` é a exceção documentada da anti-recursão — nenhum secret novo, nenhum PAT). O fluxo interno do deploy não mudou: `verify` full intocado (nada publica sem verde), environments intocados (`staging` sem reviewer, `production` com required reviewer), `concurrency: deploy-homeserver` (`cancel-in-progress: false`, `queue: max`) segue só nos jobs de deploy, nenhum auto-retry/cancelamento de runs antigos, nenhum workflow gêmeo e `scripts/deploy-homeserver.sh` intocado (pin `deployScript.unit.spec.ts` verde sem edição). O pin unitário do manual-only virou o pin do novo contrato (`ciSkipInvariants.unit.spec.ts`: push em `main` + guard + dispatch + requeue), com `deployTrigger.unit.spec.ts` novo e casos novos em `githubApi.unit.spec.ts`. Riscos operacionais documentados no runbook (`docs/ops/teqo-1313-deploy.md`): um approval pendente segura o grupo de concurrency (staging de runs novos espera) e um merge durante `deploy-production in_progress` só converge no próximo merge/dispatch — ambos com gatilho de revisitação. O anti-goal "manual-only" da OPS102 fica superseded: automatiza-se o **início** do run, nunca o approve de produção.
